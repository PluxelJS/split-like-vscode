## 验证顺序

1. 核对个人分支、工作区、跟踪、相对集成主线差异及实际 gitlink，保留已有改动。依赖以实际安装及锁文件分别记录。
2. 原生补丁变动先运行 `pnpm test:native`：同版本未补丁反例、五类 history、完整 blocker 后复核、重载/重试 redirect、
   原生拒绝/取代/后台结算、source/ESM/CJS/声明、唯一原生对象以及独立浏览器拖拽。安装器随包交付，版本相同不等于具备能力。
3. 公开只读、真实保存编辑器、工具/定制菜单始终复用 [demo examples](../../packages/demo/src/examples/)。
   编辑例子保留实际持久化、保存期间新增编辑、重叠暂停与释放；隐藏文档的确认仍须可操作，不能用占位函数或强制激活规避。
4. 定向行为稳定后按各仓库标准执行一次提交前 verify，任务/文件串行并保留缓存。源码类型、真实 Router/Model、
   生产浏览器、独立 tgz 与实际宿主分别记录。新代码或失败再做相应检查，纯文案修正不重跑全套。
5. 独立消费者从实际 tgz 安装，执行包内离线原生安装器；同一组示例检查 JS、严格类型、CSS、原生对象唯一性与交互。
   SplitView 另做只有 React 的独立安装，不要求 Router/FlexLayout/Hotkeys 或已删除的 core。
6. 财务按现行业务保护验收桌面、窄窗格、实际 2×2、焦点、滚动及资源释放，不重设计会计、CAS、回执或共享草稿。
   操作运行宿主遵循其本地 skill 和 dev-console HMR batch；实例不存在时不能声称已经完成宿主验收。
7. `pnpm measure` / `pnpm measure:native` 先验证行为，再记录 2/10/50/200 文档、读取、切换、分组与关闭的实际工作量和时间。
   仅对相同工作负载和证据比较；没有等价历史基线时只报告当前测量与限制。
